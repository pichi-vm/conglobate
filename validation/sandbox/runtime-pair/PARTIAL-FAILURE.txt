Paired runtime mounts: bounded setup-error teardown
==================================================
Reproduce:
 python3 validation/sandbox/guest.py runtime-pair \
   --kernel-version 7.2.10-200.fc44.x86_64 \
   --out /tmp/conglobate-runtime-pair-partial-NEW --run
Evidence: reproduced/runtime-pair-partial (guest exit zero).

The validation-only safe Rust helper accepts an optional count1..6. After the
corresponding successful mount syscall it emits the exact count and returns an
error. The launcher uses set -eu, so it exits without running the inspect/recipe
continuation. Normal two-root invocation remains unchanged.

Six cases exercise errors after tool proc/dev/sys and output proc/dev/sys in
order. Each confirms preflight completed, the intended count was reached, the
helper failed with the injected error, and neither successful-setup nor next-
command markers appeared. subprocess.run waits for namespace launcher exit.
The outer mount table and owned canary are unchanged; all six underlying runtime
directories and the tool output attachment directory remain empty. The fixture
can remove its owned directories. The original19 controls also pass again.

This qualifies ordinary setup-error lifetime in this single-child private mount
namespace topology. No manual unmount is used for a passing case. It does not
inject mount syscall errno, prove kernel-resource reclamation timing, qualify
retained namespace descriptors or background descendants, test SIGKILL between
individual mounts, or replace the existing full-build cancellation tests. No
filesystem worker runs in this small fixture. No production helper changed.
