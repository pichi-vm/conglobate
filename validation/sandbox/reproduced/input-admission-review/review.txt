Image admission: measured bytes, interpretation and error propagation
====================================================================
Source reconciliation, not a new runtime pass or permission to weaken the design.
Grounding: DESIGN.md trust model and image pipeline; src/cache.rs, src/scute.rs,
src/build.rs; pinned carapace assemble/snapshot/verity validators; retained
chain-header, exception-kernel/termination, compressed-declared-bound and
snapshot-wire-bounds evidence. Sources for this review are retained separately.

Actual boundaries
-----------------
1. Cache copying verifies regular-file type, exact descriptor size and digest
   while copying into private storage. A failed copy can leave untrusted private
   scratch bytes; callers must not treat those as admitted. No original cache
   pathname is substituted for the retained staged copy during assembly.
2. Staging validates supported manifest verity parameters; decodes compressed
   streams, enforces declared decoded extent and complete stream consumption;
   reconstructs verity roots including the defined final-block padding; and
   resolves the complete parent-root chain. Duplicate/disconnected/missing
   ancestry and mismatched trusted roots are rejected. Source comments explicitly
   state this does not validate snapshot exception semantics.
3. Carapace validates its supported header contracts and constructs the read-only
   authenticated stack. Its snapshot header is read through verity before the
   snapshot target is activated. Header rejection and cleanup already have a
   correctly-hashed positive/negative matrix.
4. The trusted kernel interprets snapshot exception records and services reads.
   Existing bounded cases distinguish assembly rejection from read-time EIO and
   tolerated noncanonical interpretations. Metadata-as-data reads bytes from the
   same authenticated owned store; it does not demonstrate access to unrelated
   storage. Duplicate exceptions are characterized, not silently declared invalid
   by an invented additional format rule. Missing metadata termination at the
   tested area boundary rejects assembly; the next-area positive control passes.
5. Filesystem interpretation belongs to the selected trusted filesystem worker
   (and kernel for the relevant direct mounts). Authentication of bytes does not
   prove filesystem usability or parser memory safety. Those implementation and
   hostile-input handling obligations remain part of the trusted worker review.

What the design does and does not require
----------------------------------------
The design requires verified inputs, command isolation, correct output lifetime,
error propagation and stable inventory/publication. It trusts the build kernel.
It does not specify a second userspace parser that duplicates every kernel
snapshot/filesystem interpretation or a canonical exception-list policy stricter
than the supported ecosystem format. Such a policy would require an explicit
format/compatibility decision, not an implied new checklist requirement.

Consequently, 'semantic admission policy unfinished' was too vague as a standing
gate. Replace it with actual supported format constraints and error propagation
through the selected executor. Do not claim staging alone rejects all malformed
COWs. Do not silently treat a tolerated kernel interpretation as a security bug
or relax an existing header/verity/ancestry constraint. Existing diagnostic input
mutations deliberately recompute valid hashes so rejection cannot be attributed
only to an authentication mismatch.

Remaining qualification
------------------------
Current Environment::mount propagates chain assembly failure before snapshot/
filesystem/recipe execution; the top-level build publishes only after success.
This is source evidence, not the missing generic restricted-executor runtime
integration. The fixed publication fixture covers captured committed inputs,
command success/failure, inventory binding and publication; it is not arbitrary
recipes. Final integration must check actual stage/mount/read/finalization failure
paths against publication eligibility, using the selected worker's error contract.
A command handling an ordinary I/O error is not automatically equivalent to a
trusted worker failure; the builder cannot infer arbitrary recipe intent from
stderr or certify semantic correctness of author-created files.

Declared extent enforcement bounds written decoded bytes, not all decoder CPU/
internal allocation; undeclared extents retain their existing contract. Resource
limits, immutable staging/control paths and lifetime ownership remain necessary.
No finite malformed-input suite proves all parser behavior or kernel safety.
No validated filesystem-semantic requirement, build-failure rule or measured-input
binding is waived by this reconciliation. Broader final-executor tests remain,
while another speculative exception parser is not a prerequisite for the goal.
