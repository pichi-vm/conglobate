Set-ID exec and no_new_privs — 2026-10-21
=======================================
Bounded guest-only comparison. The executable is a safe-Rust credential reporter
with forbid(unsafe_code); it only reads its own credential status and prints
UID/GID/capability/NNP/seccomp fields. It has no shell/command execution interface.

The fixture copies this binary to its owned image tmpfs, assigns host-guest
UID/GID100000 (mapped namespace UID/GID0), then mode06755. The trusted launch root
and runtime are otherwise the existing policy fixture. No host executable is
modified and no initial-userns-root privilege is conferred by these ownerships.

A baseline private mapped-user/PID/mount/network/IPC/UTS launch omits the candidate
restrictions. Its Python test spawns only the fixed reporter after setting real
UID/GID1234 and clearing supplementary groups. The reporter must show real IDs
1234, effective IDs0, nonzero capabilities and NNP0. This positive control proves
the selected set-ID executable/mount setup can confer privilege within that
mapped namespace, rather than merely assuming it was suppressed by nosuid.

Both ordinary restricted policy steps run the same reporter after the same ID
drop. It must show real/effective UID/GID1234, zero effective capabilities, NNP1
and seccomp mode2. The invoking mapped-root process's identity/capability/security
fields remain unchanged. This ties the no-new-privileges boundary to actual exec
of a set-user-ID/set-group-ID binary, not just reading NoNewPrivs at command entry.

Source context: retained pinned security/commoncap.c examines
LSM_UNSAFE_NO_NEW_PRIVS in exec credential handling. Namespace mapping and the
entry policy remain separate prerequisites; NNP is not a substitute for them.

Limits: one owned set-ID reporter, mapped UID1234 and this tmpfs runtime. It does
not qualify all setresuid/securebits transitions, executable file capabilities,
FUSE nosuid behavior, dynamic loader identity or distro package helpers. Positive
control has no restrictions; it is test setup, not a proposed command policy.
The existing metadata/UID-lifetime/runtime-binding gaps remain open.
