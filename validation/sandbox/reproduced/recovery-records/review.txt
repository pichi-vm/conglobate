Protected record recovery candidate — 2026-10-21
================================================
Diagnostic fixture only; not an adopted record encoding or production API.
Run guest.py chain-recovery-records with the standard kernel/worker arguments.

This extends the completed real FUSE build fixture. Its owner has finished,
command descendants are gone, storage cleanup passed, and the original complete
artifact is copied into per-case mode0700 directories. A trusted harness writes
an atomic prepared record before starting the existing safe-Rust commit arbiter.
The record contains a version, staging directory device/inode, and complete file
hash map. The paths are fixed by the fixture, not supplied by the record. The
arbiter still uses NOREPLACE. After its actual process is killed and reaped, a
fresh Python process classifies filesystem state without the earlier replies.

Candidate outcomes:
- PreparedNotVisible: the original staging directory and bytes remain, no output
  exists, and no completion receipt contradicts that state.
- Collision: original staging remains but some destination exists; preserve both.
- VisibleAcknowledgmentUnknown: the original directory is now at the output,
  all expected file bytes match, and no receipt establishes acknowledged commit.
- Committed: matching output plus protected receipt naming the prepared-record
  digest, written only after the coordinator's Committed reply.
- Unknown: absent/malformed records, inconsistent receipts, absent/altered output,
  or unsupported object types. Do not retry/delete based on this classification.

The receipt means the trusted recorder received Committed; it does NOT mean an
external client received a success reply. Losing a reply to that client remains
possible. Likewise no receipt does not prove the coordinator failed to sync.
Receipt parsing is diagnostic JSON so inspection is straightforward. This does
not propose JSON for the ecosystem; production machine formats remain CBOR.

Critical assumptions and limits
-------------------------------
Directory device/inode identity is useful only inside this protected parent,
within the same filesystem lifetime, with no deletion/reuse by another actor.
It is NOT a globally unique attempt identifier or a portable authenticated
receipt. Retained file hashes distinguish byte changes but do not independently
prove completion eligibility or identity. Hash equality alone cannot attribute
an identical foreign destination to this attempt. No content/parent path races
are allowed by the fixture; no symlinks or special entries are accepted as the
output artifact. Modes/xattrs are not included in this diagnostic identity.

The supervisor/record writer remains trusted, records cannot be edited by recipe
commands, and no peer recoverer runs concurrently. This test does not compose
record recovery with the cooperative lease or prove that all writers hold it.
A real implementation needs a protected stable recovery namespace, exclusive
attempt ownership, validated parent handles and a recovery admission protocol.
No orphan deletion or automatic retry is implemented. Temporary case directories
are removed only by the harness after assertions, not by recovery.

Record install uses file sync, atomic replace, and parent sync. The actual commit
helper syncs the parent after rename. These are process-death tests on ordinary
tmpfs, not reboot/power-loss recovery. No failure inside those syscalls, hostile
record-size/resource bounds, or durability on another filesystem is qualified.
The existing production publish implementation has no such recovery record.
