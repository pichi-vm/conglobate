Candidate mount API coverage review — 2026-10-21
===============================================
Reviewed entry/helper/src/main.rs against current host UAPI and pinned upstream
Linux f47d223627f80cb7a1eb14c585fe6cb35de5e984. This is diagnostic policy review,
not production integration or a complete syscall/interface qualification.

Findings and corrections
------------------------
The candidate denied open_tree and mount_setattr but omitted open_tree_attr.
Pinned fs/namespace.c implements open_tree_attr as tree acquisition plus optional
mount attribute application; the x86_64 table and asm-generic UAPI assign467.
The Linux manual describes it at:
https://man7.org/linux/man-pages/man2/open_tree_attr.2.html
libc0.2.191 in this helper does not export the constant, so the rule uses467
explicitly under x86_64/aarch64 cfg. Runtime testing is x86_64 only; aarch64 is
source-number corroboration, not a tested target.

A baseline restricted command created a detached mount of its own newly made
empty directory using OPEN_TREE_CLONE|CLOEXEC, no attributes, then closed the FD
and removed the directory. Both successive command namespaces reproduced this
omission. No mount was attached, no outside path used, no mount flags relaxed.
This is evidence that the declared mount restriction was incomplete, not a
sandbox escape. After correction, the same valid call returns EPERM in both
steps, as does a separate null-argument dispatch check.

fspick was also missing. Pinned fs/fsopen.c opens a reconfiguration context;
actual reconfiguration is a separate operation, and fsconfig was already denied.
The correction denies fspick too. An unrestricted trusted fixture control opens
and closes a context for its owned /work tmpfs without changing it; restricted
commands attempt their private /dev tmpfs and must get EPERM. This positive
control establishes syscall availability on an owned mount, not that identical
credentials/paths were used on both sides. The null-argument check independently
requires policy rejection before kernel argument validation.

Current explicitly denied acquisition/mutation APIs
---------------------------------------------------
mount, umount2, pivot_root, fsopen, fspick, fsconfig, fsmount, open_tree,
open_tree_attr, move_mount, mount_setattr. Namespace unshare/setns, namespace
clone flags and clone3 are separately restricted as documented in README.txt.
The policy still defaults to Allow. Read-only mount/namespace queries, generic
ioctls and other FD acquisition paths are not automatically covered by this list.
In particular, statmount/listmount/listns and new file_getattr/file_setattr APIs
need distinct semantic review; they are not reclassified as mount mutation merely
because they appear near these calls in the syscall table.

Evidence and limits
-------------------
reproduced/open-tree-attr-source retains fs/namespace.c, fs/fsopen.c and both
number tables with hashes/URLs. open-tree-attr-baseline is an expected negative;
open-tree-attr-fixed records the first correction; mount-api-policy is the
combined correction/control matrix. Capability/FD/process/network/ioctl and
ordinary file/thread checks remain in the same two-step policy run. No new
capability is granted and no crate dependency is added. Larger distribution
workload compatibility, future syscall additions, complete reachable-object
review and final-executor integration remain open.
