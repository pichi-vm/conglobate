UML architectural candidate review — 2026-10-21 UTC
==================================================
Source-only comparison, not selection, implementation, runtime validation or a
waiver of the standalone conglobate requirements. All nine primary files are
pinned to Linux f47d223627f80cb7a1eb14c585fe6cb35de5e984 in sources.json.

Why it might address the specific blocker
----------------------------------------
The existing mapped-FUSE failure occurs before dispatch to the filesystem worker:
host VFS insists on initial-userns capabilities. A full Linux kernel running as
an ordinary host process would evaluate the filesystem's permissions in its own
kernel. With a native block filesystem there, trusted.*, mknod and inode flags
would no longer be operations on host FUSE inodes. This is an architectural
inference, NOT evidence that the complete proposed setup works.

Pinned arch/um/drivers/ubd_kern.c open_ubd_file opens host paths through
os_open_file and locks them unless shared mode is requested. do_io performs
positioned reads/writes and maps flush to os_sync_file. The file wrapper lives
in arch/um/os-Linux/file.c. This provides a concrete potential byte-I/O boundary;
no proof here of compatibility with the existing dm snapshot, exclusive access,
flush failure propagation, cancellation, layer sealing, or all block ioctls.
A direct block-backed filesystem is the relevant candidate, not hostfs.

Constraints that prevent treating stock UML as the answer
--------------------------------------------------------
1. HOSTFS deliberately accesses host files. It should be excluded from a
   candidate configuration, not offered to recipe commands. The official guide
   warns about unrestricted hostfs access. A restricted outer filesystem view
   and inherited-FD review would still be needed for all other host-facing code.
2. MCONSOLE defaults on in the pinned Kconfig. Management and dynamic device
   configuration need exclusion or a protected control boundary. Do not allow
   image-selected kernel modules or driver parameters to add host-path access.
   The trusted kernel and its build configuration become runtime inputs.
3. A kernel in userspace remains a kernel runtime dependency. It avoids the
   need for KVM hardware but is not the existing namespace/FUSE design. User
   acceptance is pending; this review does not redefine standalone conglobate.
4. The current guide's blanket uniprocessor statement is insufficient: pinned
   arch/um/Kconfig has conditional SMP with limitations for threads within one
   userspace process, and arch/x86/um/Kconfig selects the subarchitecture option.
   No throughput or concurrency promise follows without a configured build/test.
5. Runtime licensing: pinned COPYING declares GPL-2.0 with Linux-syscall-note;
   the full license and exception are retained. An external kernel executable
   is distinct from linking kernel implementation into conglobate. Distribution
   must account for the kernel's own license; no legal compatibility certification.

A discriminating test, only if this architecture is considered
-------------------------------------------------------------
Build a pinned minimal UML kernel, run it as an unprivileged UID inside a
separate disposable validation guest, with no hostfs, networking or management
socket. Give it only an owned scratch filesystem image. Run the existing
metadata operations (including enforcement and clear inherited flags), then
shut down and verify the disk using an independent kernel mount/fsck. Kernel
configuration, output hashes, process credentials and relevant descriptor
admission must be retained. This is a feasibility test, not a production change.
If that passes, actual authenticated layering, representative OS build,
completion/cancellation, resource limits and host-interface isolation remain
mandatory. No extra parallel validation list supersedes the original 21 areas.
