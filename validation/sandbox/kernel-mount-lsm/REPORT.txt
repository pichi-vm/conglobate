Kernel ext4 + idmapped mount + scoped BPF LSM validation
=======================================================
Result: the mechanism works without FUSE or command CAP_SYS_ADMIN on the tested
x86_64 Fedora kernel, with SELinux disabled in the disposable build guest.
This is feasibility evidence, not production sandbox approval.

Topology
--------
The trusted guest supervisor creates a disposable ext4 image on RAM-backed
storage and mounts it with the kernel driver, nosuid,nodev. It clones the mount
and uses mount_setattr(MOUNT_ATTR_IDMAP) with the command user namespace mapping
0..65535 to outer 100000..165535. The superblock remains owned by the initial
user namespace. It does NOT move into the command user namespace.

The command receives only the mapped filesystem view. It has private mount,
PID, network, IPC and UTS namespaces, no-new-privileges and a default-deny syscall
filter. SYS_ADMIN is absent from effective, permitted, inheritable, ambient and
bounding sets. No FUSE worker runs. Block-device/image paths, supervisor files,
context files and policy-control handles are absent from the command sandbox.
The fixture mounts supplied tools read-only and performs an offline package
installation; it is not a production carapace/snapshot implementation.

The policy independently binds the authorized command user namespace/root UID
and the target superblock owning namespace/device ID. This replaces the FUSE
prototype's requirement that both namespaces be identical. Only the exact
security.selinux attribute receives the capability-check exception. Ordinary
filesystem permission checks and other LSM hooks still apply. Loader death
leaves the complete policy pinned; namespace and mount lifetimes remain held.

Successful checks
-----------------
- Before installing policy: ordinary reads work, security.selinux set/remove
  fail without SYS_ADMIN. After removing policy, mutations fail again.
- With policy: create/replace/remove, fd operations, hardlinks and symlink labels.
- Longer security.selinux-prefixed attribute names are denied, as are unrelated
  security/trusted names; nonroot labeling is denied.
- A second writable idmapped ext4 filesystem, with the SAME superblock owning
  namespace but a DIFFERENT device ID, permits ordinary writes and denies label
  set/remove. This exercises the filesystem-specific guard independently.
- A descendant user namespace with the same underlying root UID cannot label
  the output. The command's tmpfs also cannot receive the label exception.
- Namespace manipulation is denied by the installed filter. Command descriptors,
  private network routes, capability sets and hidden supervisor paths are checked
  by the reused sandbox probes. These are selected controls, not an escape proof.
- Ownership, POSIX ACL access/default inheritance, supplementary-group access,
  setgid preservation and file-capability writes succeed.
- The offline Fedora fixture installs 69 supplied RPMs, queries installed
  packages and executes installed Bash/Python in the install root.
- Native read-only ext4 remount verifies unshifted ownership (including
  UID1234/GID2345), ordinary v2 file-capability bytes, ACL presence, setgid and
  foreign labels, including the installed Bash label. e2fsck passes.
- Injected coordinator failure with a live command and forked sleeping child:
  quiescence is established before policy removal, then mounts and namespace
  references are released. No live commands or FUSE connections remain.

Reproduction and evidence
-------------------------
run.py accepts a new output directory and optional --failure. It reuses the
previous verified Fedora package guest seed at
/var/tmp/conglobate-cap-review-fix-normal-v1 and its kernel/command launch code.
Compile label-policy.bpf.c with the same clang BPF include paths documented in
../capability-review/README.txt, producing
/var/tmp/conglobate-cap-review-bpf/kernel-label.bpf.o.
Compile label-loader.c with the same libbpf paths, producing kernel-label-loader
in that directory. All kernel mounts and policy loads happen in the no-NIC,
no-disk/no-host-share disposable VM, never in the host kernel.

Final evidence: ../reproduced/kernel-mount-lsm/normal and failure.
Actual generated scripts, input hashes, guest command, output, verdict and
kernel/initramfs hashes are retained. The driver still reports
production_qualified=false. Earlier exploratory runs remain in /var/tmp.

Limits and design consequences
------------------------------
Tested ext4 only, x86_64 only, with SELinux compiled in but boot-disabled; not
permissive mode, an enforcing host policy, or a kernel lacking SELinux support.
No Arm, confidential-hardware, other filesystems, full OS boot, NAT/DNS,
resource-exhaustion, concurrent-build, abrupt supervisor-death or partial-policy-
installation qualification is claimed. The fixture's 65536-ID mapping and
hardcoded root UID are not a final production allocation scheme.

Native mounting removes the userspace filesystem worker boundary and exposes
native filesystem driver code to command filesystem operations. Untrusted raw
block access must remain prohibited. Processing malformed filesystem images in
the shared kernel requires separate trust analysis; this test uses fresh images
created by the trusted supervisor and does not exercise malformed images.

The LSM does not make arbitrary filesystem operations privileged, enable every
xattr namespace, or remove idmapped-mount support requirements. It delegates one
specific label operation. Stable identity ownership, policy lifecycle/attestation
and production process containment still need a complete implementation design.
No production conglobate source or normative sandbox choice changed in this test.
