Why native disk filesystems do not opt into userns delegation
============================================================
Source/history review, 2026-10-21. No kernel changes or runtime tests.

Conclusion
----------
The evidence supports an intentional conservative boundary around unaudited
filesystem semantics, plus the longstanding risk of parsing hostile disk
metadata in the kernel. It does not establish a fundamental impossibility
of privileged delegation. No driver-specific rejection of a completed ext4,
XFS or Btrfs FS_USERNS_DELEGATABLE implementation was found in this search.
Absence of a flag is not proof that a complete implementation was proposed
and rejected, nor proof that enabling it would be safe.

Primary upstream rationale
--------------------------
1. Seth Forshee's July 2024 patch explains that child-fsopen followed by
   privileged-parent creation previously allowed non-initial s_user_ns for
   most filesystems. It closes that path because filesystems without the
   opt-in cannot be presumed to support that ownership model. The stated
   rationale is increased bug/security risk, not a reported per-driver
   exploit or an impossibility theorem.
   https://lkml.iu.edu/2407.3/00528.html

2. In the July/August 2025 fuse+iomap discussion, Christian Brauner expressly
   distinguishes mounting arbitrary images in a user namespace from delegating
   a filesystem to it. He describes delegation as feasible and cites bpffs
   as an existing example. The same discussion identifies kernel metadata
   parser exposure as a motivation for userspace filesystem implementations.
   https://www.spinics.net/lists/linux-ext4/msg102765.html

3. The 2026 NFS delegation change supplies the separate flag. Its privileged
   daemon validates the server before creating the child-owned filesystem;
   unrestricted child mounting remains prohibited. This demonstrates that
   vetted mount creation and child superblock ownership can be separated.
   https://kernel.googlesource.com/pub/scm/linux/kernel/git/vfs/vfs/+/c5d6cac28646b0d5d81ef632be748ae93c1f36c7

4. Historical ext4 discussion separates malformed static images from changing
   the raw device underneath a mounted filesystem. Theodore Ts'o expresses
   willingness to fix static-image bugs but explicitly excludes a blanket
   commitment to defend concurrent hostile raw-device mutation. This is
   historical rationale, not a current completeness/security guarantee.
   https://lkml.rescloud.iu.edu/hypermail/linux/kernel/1511.2/02745.html

What would actually require auditing
-----------------------------------
The superblock namespace participates in permission and ID interpretation,
not just label storage. The source snapshot retained in REVIEW.txt shows:
- vfs_cmd_reconfigure (fs/fsopen.c:254) checks CAP_SYS_ADMIN against s_user_ns.
  Changing ownership changes who passes this gate. Actual reachability also
  depends on supplied FDs, mount visibility and sandbox syscall restrictions.
- Ext4 reads reserved-block UID/GID using init_user_ns
  (fs/ext4/super.c:5399). A child-owned implementation must define whether that
  behavior is intended and consistent with its inode/ACL/quota translations.
  This is a concrete audit example, not a discovered privilege escalation.
- The core inode ID helpers use s_user_ns. Ordinary inode translation, file
  capabilities, ACLs, quotas, filesystem-specific ioctls, mount/reconfigure
  options and shared-superblock lifetime need coherent namespace semantics.
  Do not mechanically replace every capable() or init_user_ns occurrence;
  some operations intentionally retain initial-namespace authority.

Relevance to conglobate
----------------------
The supervisor selecting the device, assembling private snapshots and keeping
all raw backing storage/FDs away from commands addresses the concurrent raw-
mutation concern. Commands writing files through the filesystem are different
from commands directly rewriting its metadata blocks behind the driver's back.

Content hashes prove identity and integrity, not filesystem-parser safety.
Bootstrap output is produced by untrusted commands and can contain arbitrary
filesystem bytes, even when it is subsequently measured. Native mounting of
that output would still put the metadata parser in the trusted kernel.
Our threat model trusts the kernel; this parser exposure is nevertheless a
real difference in what the implementation asks that kernel to handle.

FUSE moves filesystem-format parsing into a worker, but our worker is explicitly
trusted too. A worker compromise is not harmless and is not contained merely
by calling it a userspace implementation. Its authority and publication access
remain part of the design. No new worker-compromise guarantee is claimed.

Our command filters can restrict remount/configuration/ioctl reachability.
That narrows the interface needing qualification; it does not prove the driver
supports a new superblock ownership model or justify silently enabling it.

Engineering conclusion: privileged delegation is plausible in principle.
Qualifying it for these disk filesystems is driver/kernel work, with upstream
review and tests, rather than an existing conglobate mount option. This review
does not recommend implementing that work or changing the chosen architecture.
