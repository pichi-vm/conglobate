Publisher/recovery exclusive ownership prototype — 2026-10-21
============================================================
Extension of the fifteen-case real-artifact record matrix, not production code.

The safe-Rust commit-arbiter creates a protected mode0600 recovery.lease inode
and holds nix::fcntl::Flock<File> exclusively before binding its control socket.
The guard remains in the main listener scope until process termination. No lock
FD is passed to recipe commands. Creating a second publisher on the same attempt
fails create_new instead of recreating/unlinking the existing lease inode.

Every fresh recovery process opens that existing inode with O_NOFOLLOW/CLOEXEC,
requires a regular file and attempts exclusive nonblocking flock. Lock conflict
returns Busy before reading records or artifact identity. Missing/invalid lease
returns Unknown. The FD remains held throughout classification. No writer is
stopped or output removed by recovery.

Each of fifteen cases adds two ownership controls:
1. After the publisher's private readiness/reservation protocol, a new recovery
   process returns Busy while the publisher remains alive.
2. After actual publisher kill/reap, one fresh reader holds the exclusive lease
   at a bounded gate. A second reader returns Busy. Releasing the first gate
   produces the same expected filesystem/record classification as before.
The inode remains unchanged; before/after file hashes show no reader mutation.
The earlier real rename, post-rename sync, receipt-write, collision and invalid
record controls remain included. A waiting fixture reader is always reaped and
is terminated if its bounded protocol fails.

Important limits discovered by source review
--------------------------------------------
There is an INITIALIZATION GAP between create_new of the lease inode and acquiring
its lock. These tests start after the readiness protocol and do not cover that
gap. A reader could briefly acquire the new inode before publisher ownership is
established. Read-only classification is all this probe does, but a future GC
must not interpret that as permission to delete. Candidate remedies include
publishing an already-locked temporary lease inode atomically, with absent lease
remaining Unknown, or an independent protected attempt-registration protocol.
This gap must be closed/validated before general recovery admission is adopted.

The lock covers the publication coordinator, not the earlier filesystem worker
and command lifetime. Those have already completed in this fixture. Their lifetime
composition, receipt-writing delegation, protected parent handles, stale temporary
records and orphan cleanup remain separate requirements. The harness is the
trusted recorder cooperating with the publisher, not a competing independent
record writer. Locks are advisory; excluding untrusted processes from the parent
and never handing them shared lease descriptors remains mandatory. No durability,
malicious-parent or arbitrary filesystem claim is made.

Atomic lease publication correction
----------------------------------
The initialization gap described above is corrected in the current diagnostic
helper: create recovery.lease.new exclusively, acquire Flock on that private
inode, then renameat2(NOREPLACE) it to recovery.lease while retaining the guard.
Recovery opens only the final name. An absent lease stays Unknown. Startup never
replaces a stale final/private name, and does not infer absence of writers from
that failure. This changes diagnostic admission only, not production cleanup.

bootstrap.py exercises actual tmpfs/process behavior with a gate after locking
but before publication. Four checks pass: death at this gate leaves no final
lease and Unknown recovery; publication exposes the same already-locked inode;
publisher death releases it without changing identity; an existing final lease
causes EEXIST and preserves both the prior inode/bytes and private failed attempt.
The fixture has no build commands or external files. The complete artifact
matrix is separately rerun with the corrected helper. This does not solve stale
lease/temp collection or the earlier build-worker lifetime composition.
