Publication and cancellation: candidate coordinator contract
============================================================
2026-10-21 UTC. Proposal for validation, not an adopted CLI/API or completed
runtime protocol. The existing new-output-directory requirement is preserved.
The source snapshots and tests cited below are the grounding for this proposal.

What existing evidence establishes
----------------------------------
- src/artifact.rs copies/syncs staging contents, checks cancellation, performs
  NOREPLACE rename, and returns. It does not arbitrate a cancellation response
  with rename through a shared state transition, or sync the destination parent
  after rename. This description is not a claim of required power-loss durability.
- chain-commit-gate waits for owner completion and resource checks before making
  its internal artifact public. A real live-descendant check rejects publication.
- chain-commit-death demonstrates death before rename (private staging remains)
  and after rename (complete public output without a returned success). EEXIST
  protects both foreign destinations and re-staged retries from replacement.
- chain-release-error demonstrates that a successful command still requires a
  successful worker finalization status. Otherwise sealing/publication is denied.
- Earlier cancellation gates demonstrate publication can follow receipt of a
  signal after the final cancellation check. Signal receipt alone is therefore
  not a promise that output is absent. No current cancellation acknowledgment
  API is assumed to make that stronger promise.

Candidate ordering
------------------
1. The trusted completion barrier establishes all of: command descendants gone,
   writer access revoked, successful filesystem finalization, stable finalized
   bytes, authenticated input/output inventory, and satisfied required cleanup
   checks. A stdout marker from recipe code cannot supply this authority.
2. Prepare a complete private artifact outside the command's reachable tree.
   Stage any cross-filesystem copy beside the destination and finish its content
   and directory checks before reservation. This operation remains cancellable.
3. One trusted coordinator serializes cancellation admission and commit
   reservation. If cancellation wins before reservation, prevent any future
   rename for that attempt; teardown remains mandatory. Acceptance means no
   output from this attempt will become public, not that cleanup already ended.
4. If reservation wins, later cancellation is pending, not acknowledged as
   cancellation accepted. Report the eventual commit/failure outcome. A single
   check of an atomic flag followed by rename does not implement this arbitration.
5. Perform NOREPLACE rename under the reserved attempt. The rename is the
   visibility boundary, distinct from reservation and caller acknowledgment.
   Never overwrite a destination or delete it to make a retry work.
6. If parent synchronization is part of the selected storage contract, perform
   it before reporting committed. A sync failure after rename must report that
   output is visible with an error, not a no-output failure. On ordinary tmpfs
   this is not a promise of persistence across reboot or power loss.
7. A normal committed reply identifies the finalized artifact/inventory.
   Process death or lost reply creates an unknown outcome for the caller;
   neither a cancellation request nor missing success output resolves it.

Outcome vocabulary for the coordinator (not new CLI syntax)
------------------------------------------------------------
- Cancellation accepted: reservation was prevented. Cleanup still runs.
- Failed before visibility: this attempt did not rename output into place.
- Destination collision: NOREPLACE lost; preserve destination and staging.
- Visible with error: rename succeeded but a required subsequent operation failed.
- Committed: selected completion/visibility/acknowledgment requirements finished.
- Unknown: observer lacks enough trusted evidence to classify commit outcome.
A failure to write an acknowledgment must never erase a visible artifact.

Recovery and orphan constraints still needing a concrete implementation
---------------------------------------------------------------------
Recovery must own the attempt exclusively and know its expected destination,
input/output identity, private staging and lifecycle state from trusted records.
It cannot interpret an arbitrary directory at the destination as this attempt's
successful output. Digest equality alone does not establish an attempt's identity
or exclude replacement during inspection. Capture/inspection must respect the
same protected-directory and stopped-writer assumptions as publication.

If available records cannot establish whether rename occurred, retain Unknown;
do not infer failure from a missing reply and automatically republish. Preserve
NOREPLACE on every retry. Any future receipt/journal or idempotency identifier
needs explicit placement, ownership, versioning and integrity rules. This draft
does not add nondeterministic fields to the inventory or invent an output format.

Orphan collection requires proof the owning attempt and all writers are gone,
plus confinement to protected, owned staging. It must not remove public output,
another attempt's staging or storage still held by a surviving consumer. Existing
snapshot lease recovery is useful evidence, not a generic artifact-GC protocol.

Finite model and what it does not prove
--------------------------------------
model.py explores all transitions in two small abstract state graphs. The negative
model combines check-then-rename with the hypothetical promise that cancellation
is accepted in between; it exhibits accepted cancellation followed by publication.
The reservation candidate admits no such trace, requires completion eligibility
before visibility, does not acknowledge commit before its modeled sync, and keeps
post-rename error distinct from failure without output. Death is Unknown rather
than falsely classified as cancellation or successful return.

This is an ordering consistency check. Its transitions assume atomic coordinator
operations and correct filesystem results. It models no process scheduling,
mutex/IPC implementation, memory ordering, path races, digest checks, permission
checks, retained descriptors, partial copying, journaling, or orphan recovery.
Those assumptions must be validated against a concrete coordinator. Existing
syscall/guest evidence remains separate and does not automatically qualify it.

Next bounded implementation validation
--------------------------------------
Implement the reservation/admission state in a diagnostic coordinator, using
safe Rust and a trusted control channel separate from recipe logs. Reuse the
already retained actual artifact and death/collision gates. Race cancellation
before and after reservation and assert the reported outcome against actual
filesystem visibility. Then add protected recovery records and prove their
behavior across the same death gates before proposing orphan collection.
No production change or requirement waiver is authorized by this document.
