Sandbox construction tools: comparative analysis for conglobate
=============================================================
2026-10-21. Source/documentation review.

FOLLOW-UP: ../runtime-validation/README.txt and its reproduced evidence now
record an execution comparison of all nine runtime/library options. This report
retains the original source-analysis scope; its proposed validation work is no
longer wholly pending. Neither report establishes production qualification.

Decision summary
----------------
Keep Bubblewrap as the preferred first integration candidate. Its strengths
are a configurable filesystem view, explicit namespace handoffs, no required
service manager/cgroup hierarchy, and the existing sibling-sandbox experiment.
Its weakness is that conglobate still owns orchestration and needs a small
worker-FD adapter. Those costs are concrete, not grounds for claiming it is
already the lowest-code production solution.

crun is the strongest executable challenger. It offers direct FD preservation,
OCI namespace joining, create/start separation and optional cgroup management.
A bounded comparison with Bubblewrap should determine whether those interfaces
remove more custom machinery than OCI state management adds. Do not choose it
merely because an OCI runtime has more features.

Youki/libcontainer is the strongest library candidate, but embedding is a
substantially larger process-model commitment than calling a library function.
Investigate cgroup selection and launch-thread behavior before preferring it
because it is Rust. NsJail is a credible command supervisor, but its namespace
joining and timer semantics fit our current contract less directly.

systemd services offer the largest supervision benefit IF a systemd manager
becomes an accepted requirement. That changes our current init-system-independent
binary contract. systemd-nspawn is not the best fit for the precise persistent
filesystem environment we specified. unshare alone saves too little policy and
lifecycle code. A bespoke executor remains a fallback, not the default outcome
of discovering that orchestration is application-specific.

No backend selection is made by this report. SANDBOX-DESIGN.txt remains the
normative contract. No production source or installed runtime was changed.

Scope and evidence quality
--------------------------
Compared upstream Bubblewrap, crun, runc, Youki/libcontainer, NsJail, systemd
transient services, systemd-nspawn, and util-linux unshare. Downloaded five
source checkouts; sources.json records exact commits and hashes of selected
files with immutable upstream URLs. These are development snapshots, not a
claim that every feature is available in distro packages or stable releases.
Systemd documentation identifies itself as version 262; individual features
have explicit minimum versions below. Consult sources.json for documentation.

Review focuses on construction interfaces and lifecycle semantics, not a full
security audit. No exploit, malicious filesystem, benchmark, new sandbox, or
confidential-platform run was executed. Earlier two-sandboxes/ evidence applies
to its recorded Bubblewrap 0.12.0 fixture, not automatically to this newer source
snapshot or a production root filesystem. Licensing assessment covers principal
components; exact selected binary dependencies still require packaging review.

Hard requirements used in the comparison
---------------------------------------
1. Root supervisor; separate worker and command user/mount/PID/IPC/UTS/network
   domains. Namespace-root commands never acquire initial-namespace root.
2. FUSE is mounted in the intended owning user namespace with actual kernel
   permission checks. The connection goes to the separately confined worker;
   commands never see it or backing devices. Equal numeric UID maps alone do
   not make different user namespaces the same capability/ownership domain.
3. Worker receives a narrowly selected FD/device and immutable runtime. Command
   receives only its filesystem/runtime mounts. No context or supervisor handles.
4. Explicit capability, syscall/ioctl, keyring, FD and environment policies.
5. Fresh worker/remount per run, command-only timer, independent fixed setup/
   teardown deadlines, cancellation and owner-death recovery. No descendants or
   outstanding writes when accepting output. Clean worker finalization matters.
6. Optional outbound NAT and supplied resolver file, no destination filter,
   no persistent DNS injection. Offline by default. Worker always offline.
7. Native amd64/arm64, no nested virtualization, no requirement to boot a target
   OS init system. Safe APIs at conglobate's Rust boundary.

--------------------

OCI runtime configuration describes a prepared filesystem root, namespaces,
mounts, capabilities, security policy, and process. It does not require Docker,
a daemon, a registry pull, or exporting carapaces as container filesystem layers.
The OCI runtime bundle is distinct from our output OCI image-layout artifact.
Only trusted conglobate generates runtime configuration; image recipes do not
supply hooks or arbitrary runtime options.

Bubblewrap
----------
Source: bubblewrap.c; bwrap.xml; COPYING.

Useful interfaces: --userns/--userns2, --userns-block-fd, --block-fd,
--info-fd/--json-status-fd, --sync-fd, --die-with-parent, capability controls,
read-only/writable mounts, private proc/dev, and seccomp FD inputs. It implements
root switching, old-root detachment, privilege transitions and a reaping init.
No general workload --preserve-fds option was found in the reviewed parser.
--sync-fd is a lifetime mechanism, not a general worker FD delivery interface.

The existing sibling fixture carries the FUSE FD through stdin, uses a trusted
adapter inside the worker sandbox to move it to FD3, then restores null stdin.
This is a feasible explicit adapter, not transparent FD preservation by bwrap.
Production must account for the adapter's identity, dependencies, seccomp needs,
and close behavior. Avoid extra adapters for commands that need no special FDs.

--block-fd is useful for delaying execution, but its implementation ignores the
result of a one-byte read, including EOF. Do not equate that flag with a
fail-closed authenticated launch protocol. --json-status-fd reports child data;
its initial report must not be confused with successful final exec. Source also
has setup-finished/error signaling. Define exactly which event starts our timer
and how launcher failure is handled; test the composed protocol.

--die-with-parent installs parent-death SIGKILL at multiple process stages.
This is useful machinery, not proof that all pre-arm races, credential changes,
owner-thread death and FUSE finalization are covered by the flag. Retain our
independent lifetime owner and the actual failure tests. Namespace creation alone
also does not isolate inherited keyrings; explicit launch policy remains ours.

Fit: strongest current integration evidence. Avoid opportunistic '--try'
namespace options or accepting missing policy. Inspect the actual resulting
namespace ownership/mapping and capability sets, not merely the requested argv.

crun
----
Source: crun.1.md, src/libcrun/{linux.c,container.c,cgroup.c,cgroup-utils.c}.

Direct --preserve-fds N can deliver the worker connection without stdin reuse.
Use only explicitly selected consecutive FDs, and clear accidental LISTEN_FDS
or other inherited environment. Namespace paths in OCI Linux configuration let
us join the pre-created owning user namespace while independently creating the
other domains. These handles/paths must remain private and alive through setup.

create prepares a container; start releases its workload. This supplies a more
explicit lifecycle than an argv-only launcher. The worker can be started while
the command remains gated. However runtime state and init can outlive the
creating CLI; lifecycle commands do not automatically bind them to conglobate's
continued existence. We still need an owner-death mechanism and must collect the
real workload outcome, not just success from a create/start management command.

--cgroup-manager supports cgroupfs, systemd and disabled. This is a meaningful
advantage for a small standalone environment. Disabled mode sets no cgroup path;
kill-all is cgroup-based, so we must not claim the same cgroup cleanup guarantees
in that mode. Private PID namespace ownership/termination and an independent
guard would need to satisfy descendant cleanup instead. Alternatively use a
build-owned delegated cgroup without inventing recipe memory-budget policy.

crun's configurable OCI mounts can match our /run and /tmp persistence contract.
Do not use an unreviewed default spec: explicitly control /sys, devices, mount
propagation, noNewPrivileges, capabilities, namespaces and seccomp. The documented
unknown-syscall failure annotation can help avoid accidentally omitting policy.
Network namespaces are supported; conglobate still supplies NAT and our resolver
behavior. libcrun is also available, but direct C embedding needs a reviewed safe
Rust boundary and has different license/linking obligations from CLI use.

Fit: best challenger to bwrap. No new validation yet for FUSE handoff, final
mount ownership, proc visibility, blocked-I/O cleanup, or the full worker/device
contract. Do not infer those from OCI conformance or published microbenchmarks.

runc
----
Source: create.go, run.go, utils_linux.go, libcontainer/{container_linux.go,
standard_init_linux.go,configs/config.go,rootfs_linux.go}.

Provides the same useful OCI create/start/state/kill/delete model and inherited
FD support. --pidfd-socket can return a stable init-process handle, attractive
for monitoring and signaling without re-resolving a numeric PID. Runtime and
proc namespace views still need careful integration. Cgroup and lifecycle
behavior must be qualified against the selected environment.

Important correction to a superficial source search: Go libcontainer has a
ParentDeathSignal configuration field and restoration after credentials change.
That is not evidence that ordinary runc CLI invocation automatically sets it.
The reviewed source references do not establish a user-facing CLI contract that
kills all workload state on conglobate death. A detached container's survival
is valid runtime behavior, but not our desired failure policy.

Fit: credible alternative and strong implementation reference. It does not
remove our FUSE or publication protocol. Choose it over crun if the pidfd path,
packaging, or integration results outweigh crun's simpler explicit no-cgroup
option. No local speed/memory comparison was performed.

Youki / Rust libcontainer
------------------------
Source: crates/libcontainer/{Cargo.toml,src/container/{builder.rs,
init_builder.rs,builder_impl.rs},src/user_ns.rs,src/namespaces.rs,
src/process/fork.rs}; crates/libcgroups/src/common.rs.

The public builder exposes safe methods for preserved FDs, owned stdin/stdout/
stderr descriptors, bundle/root paths, executor selection and container creation.
Namespace joining exists in the implementation. This is genuinely an embedding
option, unlike Bubblewrap. It could retain policy and lifecycle coordination in
Rust while reusing container construction. Internal unsafe does not violate our
ban on unsafe code in conglobate, but API safety and process assumptions still
need review.

The reviewed library defaults enable systemd, cgroup v1/v2 and libseccomp. These
are selectable features, not inevitable dependencies. More subtly,
UserNamespaceConfig::new returns Some when creating a new user namespace;
init_builder uses that to select a systemd-style cgroup configuration even when
with_systemd(false) is requested. Do NOT conclude systemd is always required:
joining an existing namespace returns None, and the cgroup manager explicitly
routes an absolute cgroupsPath through cgroupfs on unified systems. Those are
concrete candidate paths to test with the chosen feature set. Simply disabling
Cargo's systemd feature is not sufficient evidence that all launch paths work.

No disabled/no-op cgroup manager appears in the reviewed builder/manager path.
Using cgroups for lifecycle is compatible with leaving resource budgets to the
environment, but creates a deployment prerequisite. Document it if selected.

Process creation uses clone/clone3 and post-clone Rust code. Embedding should be
prototyped in a dedicated single-threaded launcher helper, not assumed safe to
call from arbitrary async worker threads in the root supervisor. Qualification
must cover logging/allocators, signals, FD inheritance and namespace transitions.
The API returns container state and optional PTY FD; caller supervision and
finalization still remain. Apache licensing simplifies library adoption but
says nothing about whether it is the smallest security boundary.

Fit: strongest library candidate, conditional on an actual integration spike.
It is not currently justified to prefer it solely because conglobate uses Rust.

NsJail
------
Source: config.proto, cmdline.cc, contain.cc, subproc.cc, net.cc, LICENSE.

Has configurable mounts, user mappings, capability controls, no_new_privs,
explicit --pass_fd, Kafel seccomp policies, supervision, resource limits and
network attachment mechanisms. These are relevant savings over unshare.

The reviewed configuration/launcher creates or inherits namespaces; no direct
existing-userns FD/path joining interface was found. A trusted pre-entry helper
could join the FUSE-owning user namespace and disable creation of another one,
but that is extra conglobate integration. It is not proof NsJail cannot work.

The built-in time limit is jail lifetime: addProc timestamps the child before
initParent completes setup. It therefore does not directly implement our
command-only timer. Disable/replace that timing policy with our execution gate
and separate internal deadlines. Resource limits are configurable; do not
silently import its defaults as new image-build policy.

Source has explicit parent-death setup, a synchronization-channel race check,
and re-arming after UID/GID changes. This improves the child-to-NsJail link.
It does not by itself prove that NsJail's own parent is conglobate for its entire
lifetime or that conglobate death terminates both sibling domains. That outer
link and stopped-worker cancellation still need tests.

Fit: worthwhile if command supervision dominates implementation cost. Less
direct fit than bwrap/crun for this specific owning-userns/FUSE sequence.

systemd transient services and nspawn
------------------------------------
Sources: systemd.exec, systemd.service, systemd.kill, systemd-run and
systemd-nspawn upstream manuals (version 262 documentation).

Transient services can own processes independently of a CLI, enforce stop-time
kill of a whole cgroup, apply syscall/capability/filesystem restrictions, and
provide lifecycle state. PrivatePIDs arrived in 257 and UserNamespacePath in
259; NetworkNamespacePath permits joining a prepared network. A previous
comparison that considered only PrivateUsers would understate their fit.
FD transport to the service and ownership of prepared mounts still require a
specific integration, not ordinary shell inheritance through systemd-run.

The service manager, not conglobate, is the service parent. This is an advantage
for recovery only when we deliberately bind worker/command units to the build
owner's failure and order finalization. A manager-backed service may otherwise
survive the caller. KillMode=control-group does not flush a filesystem, nor does
it automatically enforce our dependency between command death and worker stop.
RuntimeMaxSec/TimeoutStartSec/TimeoutStopSec help, but exact activation/execution
boundaries must match our separate timers. Fail when namespace support is
unavailable; some systemd sandbox directives document graceful degradation.

This is a credible architecture IF requiring systemd is acceptable. It conflicts
with the current binary's init-system-independent requirement; it is not a
technical impossibility. A systemd appliance can still supervise conglobate
externally without making services the binary's sandbox backend.

nspawn offers OS-container runtime mounts, filtering, veth and resolver modes.
It can run a command without booting systemd in the target. Registration/unit
allocation can be disabled, so calling nspawn is not categorically the same as
requiring a running manager. Automatic veth address/routing integration uses
networkd conventions, not a complete general solution to our explicit NAT and
resolver contract. Its private /run and ownership-adjustment modes need careful
reconciliation with persistent image contents. Built-in resolver modes select
host/resolved files rather than directly expressing our arbitrary captured
file and confined-symlink restoration contract. These are adapter costs, not
proof that nspawn cannot be configured to work.

Fit: transient services are more interesting than nspawn if the goal is to
reduce conglobate's lifetime management. Neither is selected under the existing
standalone contract.

unshare and bespoke safe-library construction
--------------------------------------------
unshare creates namespaces, maps identities and launches a process. Options
such as --fork/--kill-child and --mount-proc help, but root layout, descriptor
closure, security policy, readiness, networking and two-worker finalization
would still be ours. Namespace creation is a small portion of our protocol.

Direct safe library calls offer precise sequencing and no external runtime
state model. They also make us responsible for reviewing and maintaining the
entire launch/root/mount/capability/FD/reaping implementation. Prefer this only
for missing narrow mechanisms or if measured integration complexity establishes
that a runtime adapter is worse. Do not treat lines of code as a security score.

Licenses and packaging
----------------------
Main component licenses from reviewed source headers/manifests:
- Bubblewrap: LGPL-2.0-or-later (COPYING contains LGPL 2.1 text).
- crun executable: GPL-2.0-or-later; libcrun: LGPL-2.1-or-later.
- runc, Youki/libcontainer, NsJail: Apache-2.0.
- systemd nspawn.c and run.c: LGPL-2.1-or-later source headers.
- util-linux unshare.c: GPL-2.0-or-later source header.
These last headers were checked through upstream raw source URLs recorded in
sources.json; they are not full repository/dependency license audits.

Invoking an independent executable is different from copying/linking its source
into conglobate. No apparent Apache-2.0 licensing blocker was identified for
these subprocess candidates. Distribution still carries license/notice/source
obligations for bundled copyleft binaries and modifications. A Rust crate
allowlist does not audit external executables. Review the exact selected native
libraries, optional features, patches and appliance distribution. For libcrun,
a safe Rust wrapper and LGPL linking obligations are additional work.

Portability and performance
---------------------------
All candidates use native Linux facilities and need no nested hardware
virtualization. That passes the architectural filter, not confidential-platform
qualification. crun release configuration includes amd64/arm64 (including builds
without systemd); Youki release/e2e configuration includes x86_64/aarch64; runc's
release targets include amd64/arm64. These are build/test declarations, not our
own deployment passes. Bubblewrap has our ordinary x86 prototype evidence;
NsJail has architecture-aware source, but this review establishes no arm64
integration pass for it. Every chosen policy needs real arm64 syscall/ioctl tests.

No comparative startup, RSS, distro-workload or failure-latency measurements
were taken. Do not reuse project microbenchmarks as measurements of our FUSE
pipeline. Per-step worker/remount costs may dominate runtime-launch differences.

What conglobate must own with EVERY candidate
--------------------------------------------
Input verification and locked cache access; carapace/dm/loop assembly; private
RAM scratch; filesystem backend correctness and patches; FUSE mount ownership
and connection handoff; confined COPY/export; explicit output paths and format
validation; NAT and exact resolver semantics (or a separately qualified helper);
step and setup/teardown policy; cross-sandbox failure ordering and independent
abort; writer revocation; clean filesystem finalization; stable-byte hashing;
inventory and atomic publication. No runtime's 'container stopped' state proves
all of those are complete.

Recommended comparison before choosing production backend
---------------------------------------------------------
Use Bubblewrap and crun in one bounded integration comparison; add libcontainer
only if embedding remains a priority. Same patched worker, filesystem image,
metadata workload and expected policy for each. Keep this separate from full
distro/CoCo qualification so tool selection does not restart all prior research.

1. Worker: pre-mounted FUSE FD, separate userns and credentials, only assigned
   backing storage, null stdin, exact inherited-FD list and effective policy.
2. Command: same owning userns as prepared filesystem, independent other
   namespaces, real image root, no old-root/worker/context/control access.
   Verify mode/ACL/foreign-label/UID/GID/capability persistence.
3. Trusted readiness and command-only timer boundary. Setup failure and launch
   channel EOF must never authorize unverified execution or successful output.
4. Normal exit, shell exit with descendants, timeout, worker death/stall,
   launcher death and supervisor death; no accepted output, live descendants,
   leaked connections or unsafe resource reuse after failed cleanup.
5. Confined DNS symlink injection without persistent changes; network-disabled
   and outbound-NAT paths; device/ioctl policy using actual snapshot storage.
6. Compare adapter complexity, required helpers/dependencies, diagnostics,
   cgroup prerequisites and measured startup/cleanup costs. Select one backend,
   rather than maintain multiple implementations without a demonstrated need.

Choose crun if direct FD passing/create-start removes enough custom coordination
while preserving manager independence and verified owner-death cleanup. Choose
Bubblewrap if OCI state/cgroup integration adds more machinery than the narrow
FD/readiness adapter. This is a testable decision, not a claim that either tool
already satisfies the final sandbox contract.
