Sandbox proposals against the mandatory confidential-platform requirement
2026-10-21

Requirement
The sandbox must operate inside confidential build VMs on Intel, AMD and Arm,
while isolating untrusted commands from conglobate and preserving the required
OS-image filesystem semantics, including independent target SELinux labels.
Reference environments: Intel TDX, AMD SEV-SNP, Arm CCA Realms. This does not
mean every cloud SKU or arbitrary provider kernel must support the appliance.
It does mean the design cannot depend on unavailable nested virtualization.

Evidence level
This is a source/documentation acceptance review against retained runtime
experiments, not three new hardware executions. The accessible local machine
reports AMD EPYC 8324P, x86_64, /dev/kvm and /dev/sev. That does not establish
an active SNP guest or provisioned confidential test environment. No Intel TDX
or Arm CCA test endpoint is established in this workspace. None of the existing
UML/FUSE results constitutes a three-platform confidential-computing pass.
No production code changed, no host policy changed, and no new guest launched.

Verdicts
1. Full initial-userns root with mount/PID/network isolation (old executor).
   Platform: no special confidential-VM hardware dependency on any platform.
   Overall: unacceptable AS PROPOSED for hostile commands. Its full capability
   profile was explicitly designed for trusted recipes. Namespace separation
   alone does not establish separation from supervisor/global kernel authority.
   Root with a carefully reduced capability/LSM profile is not categorically
   impossible; it would be a new security design and requires metadata tests.
   Historical shared-root proposal rejected. The replacement contract is in
   ../../SANDBOX-DESIGN.txt; it requires two independent sandboxes.

2. Kernel-mounted ext4/XFS/Btrfs + idmapped mount + child user namespace.
   Platform: no nested virtualization required; plausible on all three with
   the appropriate Linux configuration. Actual confidential runs pending.
   Overall: existing foreign-label blocker remains. Idmapping does not change
   superblock user-namespace ownership. Disabling/omitting SELinux leaves
   commoncap's superblock-namespace capability check; permissive SELinux does
   not make policy validation equivalent to an absent SELinux LSM.
   Evidence: superblock-ownership/{RATIONALE,REVIEW}.txt and retained sources;
   ../../SELINUX-RESEARCH.txt is historical and some tests postdate that file.

3. Native block filesystem mounted directly by child-userns root.
   Platform: not a hardware problem, but the inspected ext4/XFS/Btrfs Linux
   filesystem registrations do not grant FS_USERNS_MOUNT. Moving an existing
   mount into another namespace does not reassign its superblock owner.
   Overall: unavailable as proposed on the inspected stock kernel. Enabling
   the flag in a custom kernel is a security/kernel development project, not
   an already-supported option. See superblock-ownership/ retained sources.

4. Trusted FUSE worker + untrusted commands in a child user namespace.
   Platform: plausible on Intel/AMD/Arm; ordinary Linux FUSE/user namespaces
   require no nested virtualization. Worker binaries and syscall/ioctl policy
   must be ported and tested on arm64. Existing fixtures include x86-only
   ioctl constants and are not portable merely by recompiling the worker.
   Overall: survives the confidential-platform filter, but not yet the full
   filesystem contract. Retained mapped-FUSE tests pass foreign SELinux labels,
   ownership, ACLs (with worker correction), and capabilities. They reject
   trusted.* attributes, device-node creation, and immutable/append-only changes.
   ACL/statx worker corrections do not remove host-VFS capability checks.
   Evidence: metadata/README.txt, reproduced/clean-native-pair, acl-fix and
   statx-worker. These restrictions were subsequently accepted as explicit initial limitations;
   see ../../SANDBOX-DESIGN.txt, section 9.

5. Other FUSE backends, lklfuse, virtiofs-style name remapping.
   Platform: userspace workers can in principle run inside all three; each
   backend's maintained architecture support remains to be qualified.
   Overall: substituting a backend does not remove host-VFS checks before FUSE
   dispatch. LKL via FUSE is not an execution kernel for arbitrary build tools.
   Name remapping behind those checks does not alone fix client-side rejection.
   A virtiofs guest needing a separate kernel inherits that execution backend's
   requirements. See ../../USERSPACE-FILESYSTEM-RESEARCH.txt.

6. Userspace block devices (ublk/NBD) instead of loop/device mapper.
   Platform: Linux software facilities, no intrinsic confidential-hardware
   dependency; provisioning, kernel config, implementation and Arm tests pending.
   Overall: storage transport, not a command sandbox or solution to superblock
   ownership. Kernel mounts and FUSE retain their respective restrictions.
   Does not by itself establish an entirely unprivileged conglobate.

7. Privileged metadata broker / syscall mediation / shadow metadata.
   Platform: no intrinsic nested-virtualization requirement. Architecture-specific
   syscall decoding/filtering and safe concurrent object handling are required.
   Overall: still a research candidate, not disproved by confidential computing.
   Read/write/list/remove, inherited metadata, FD/path races, inode semantics and
   faithful materialization are unsolved integration obligations. Final setfiles
   alone is not transparent metadata support during commands. See historical
   SELINUX-RESEARCH.txt. A custom delegated-metadata kernel API is likewise new
   implementation work, not an existing facility we have validated.

8. Stock gVisor syscall virtualization.
   Platform: distinguish systrap (software) from KVM (requires nesting in a VM).
   Systrap is the relevant portable candidate; exact amd64/arm64 releases still
   need build/runtime qualification. KVM is rejected as the universal baseline.
   Overall: inspected stock gofer path rejects system/trusted xattrs and writes
   to security xattrs, and restricts mknod. It is not a ready-made filesystem
   solution. A custom sentry/backend is a substantive new proposal.
   Evidence: pinned gVisor 8a05f48c4c1b1da0bbb360abf8df41ca9302cfbb analysis in
   USERSPACE-FILESYSTEM-RESEARCH.txt; current platform guide below.

9. UML, including the tested Debian packaged UML kernel.
   Intel/AMD: software execution mechanism has no nested-KVM dependency;
   confidential execution is plausible but not hardware-validated here.
   Arm: inspected upstream has no arch/arm64/Makefile.um or arch/arm64/um;
   arch/um/Makefile requires that architecture integration. x86 integration
   exists. Thus the existing upstream/packaged proposal fails Arm availability.
   This is not a claim that an Arm port is fundamentally impossible. An external
   experimental port would need separate maturity and correctness review.
   Full CPU emulation of x86 UML on Arm changes the backend and workload ISA;
   it does not establish native arm64 build support.
   Existing x86 results remain valid: uml-validation/RESULTS.txt. They establish
   ordinary-VM functionality and performance, not confidential-platform coverage.

10. Nested KVM (QEMU, microVM VMM, or another hardware-virtualized sandbox).
    AMD: GHCB rev2.04 section4.7 explicitly excludes nested virtualization under
    SEV-ES and SEV-SNP. This alone rejects a mandatory three-platform backend.
    Intel: TDX TD partitioning is specified, but is not evidence that ordinary
    nested KVM is available on all TDX deployments. Integration unqualified.
    Arm: documented RMM owns Realm EL2; ordinary EL2-backed nested KVM inside
    a Realm is not established by ordinary Arm KVM nesting support. Unqualified.
    Do not conflate confidential L2 under ordinary L1 with L2 inside confidential
    L1, or SNP VMPL with an ordinary nested KVM interface.
    Overall: reject as required baseline. No need to boot ordinary nested KVM
    to reconfirm a result that would not test this requirement.

11. Full-system software emulation (QEMU TCG), raised after UML validation.
    Platform: QEMU documents TCG hosts for both x86 and Arm, and system targets
    for x86_64/aarch64. No /dev/kvm or virtualized hypervisor mode is required.
    Thus it survives the architecture/dependency filter on all three platforms.
    Overall: candidate, NOT an end-to-end pass. Inner Linux provides native
    filesystem semantics; the entire inner kernel/runner remains untrusted.
    Outer VMM confinement, minimal device model, metadata, lifecycle, snapshot
    handoff, memory use and actual workload performance need validation.
    Unlike UML it translates CPU execution as well; no speed advantage assumed.
    QEMU user-mode emulation is different: forwarding syscalls into the outer
    kernel does not automatically provide the separate filesystem boundary.

Cross-cutting implications
Changing from bespoke namespace setup to runc/youki/bubblewrap/unshare/crun
does not change the relevant capability, superblock or hardware constraints.
Their exact support/licenses remain packaging concerns; none alone solves this.

All workers/emulators, guest RAM and mutable disk backing must remain inside
the confidential VM's protected memory boundary. Do not use an untrusted outer
host service to parse plaintext filesystems or hold emulator RAM. Swap and
shared I/O buffers are appliance concerns that must be included in deployment
qualification. Authentication of input blobs and controlled output publication
remain necessary; memory protection does not authenticate external storage.

Commands must not receive attestation/credential interfaces, supervisor IPC,
cache/context mounts or publication authority. Outer attestation measures/binds
the actual trusted appliance, enforcement components and runtime policy plus
inventory; it does not make an untrusted guest's completion message trustworthy.
Networking/DNS, namespace/cgroup restrictions and cleanup still require tests
inside each actual confidential guest. Host VPN/split-DNS support remains open.

Conclusion
No existing proposal has demonstrated the complete three-platform requirement.
FUSE/namespaces and mediation survive the hardware filter but retain substantive
semantic/design gaps. Existing UML fails Arm availability. Nested virtualization
fails the required common baseline. TCG is the clearest existing separate-kernel
candidate with documented host/target architecture coverage; performance and
actual confidential-guest validation remain open. Do not select it by elimination
or convert source-level plausibility into a claimed runtime pass.

Remaining validation for any surviving candidate
- Provision actual TDX, SNP and CCA guests; record platform/firmware/kernel,
  verify attestation mode (including debug policy), and bind runtime identities.
- Run native-architecture metadata and distro phase fixtures on all three;
  independently boot target outputs with their own SELinux policy.
- Repeat supervisor exclusion, process death, failure/publication, networking,
  memory-pressure and snapshot integrity tests in those guests.
- Verify private-memory/scratch placement and explicit shared-I/O exposure.
- Measure startup, Fedora dracut and compiler workloads; agree an acceptable
  performance envelope. No numeric performance limit was supplied by the user.
