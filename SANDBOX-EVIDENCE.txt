User namespace and idmapped mount experiment
===========================================

Environment
-----------
Fedora 44, SELinux enforcing throughout, kernel
7.2.11-dm-bufio-test1-dirty, util-linux 2.41.5.
Commands inherited unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023.
This is a custom kernel and an unconfined SELinux domain, not a validation
of a future restricted appliance profile or every supported kernel.

Method
------
Used disposable ext4 and XFS loopback images in a private mount namespace
on tmpfs. Each worker had a user namespace mapping UID/GID 0..65535 to
100000..165535, plus an isolated network namespace. The privileged parent
created a bind mount idmapped to the worker's user namespace using:

  mount --bind --map-users /proc/WORKER_PID/ns/user RAW VIEW

Workers accessed VIEW; the parent inspected RAW. After workers exited,
both mounts were unmounted and the image mounted again without idmapping
to check persisted ownership and metadata.

This was a compatibility experiment using util-linux, Python, and host
tools. It did not implement a sandbox or change conglobate's executor.
Workers retained access to host tool paths; no pivot_root, seccomp,
capability allowlist, or comprehensive descriptor isolation was tested.
The chosen subordinate ID range was illustrative, not a final policy.

Results (same on ext4 and XFS)
----------------------------
* Namespace UID/GID 0 successfully created files stored as UID/GID 0.
* chown to 1000:1000 persisted as 1000:1000, not 101000:101000.
* A named ACL entry for UID 1234 persisted as UID 1234.
* Setting the setuid mode bit succeeded and persisted.
* setcap cap_net_bind_service=ep succeeded. The raw security.capability
  attribute was revision 2, without a subordinate-root namespace ID.
* A copy of getpcaps given that capability inside the namespace was then
  executed through RAW as initial-namespace UID/GID 12345. It reported
  cap_net_bind_service in its effective/permitted sets. This is an actual
  execution check, not just successful xattr readback. An unrelated
  inherited cap_wake_alarm bit was also present in its inheritable set.
* chcon to system_u:object_r:bin_t:s0 succeeded.
* DNF5 running inside the user namespace installed a Fedora package set
  into VIEW using --installroot. Both transactions completed with status
  0 and 71 installation actions (including multilib dependencies).
  Requested packages were bash, coreutils, acl, attr, and libcap, with
  their downloaded dependencies. No scriptlet errors were reported.
* The installed /bin/sh ran via chroot as namespace UID/GID 0.
* setfiles -F -r VIEW /etc/selinux/targeted/contexts/files/file_contexts
  VIEW completed with status 0. /usr/bin/bash received
  system_u:object_r:shell_exec_t:s0.
* After relabeling, the installed shell still ran and could create a file,
  chown it to 1000:1000, and assign bin_t. Ownership and label persisted
  after ordinary remount.
* chown to unmapped UID/GID 65536 failed with EINVAL.
* mknod for a character device (1,3) failed with EPERM.
* Setting a deliberately nonexistent SELinux type failed with EINVAL.
  A parent-root control also failed; this is not evidence of a failure
  unique to user namespaces. Cross-policy labeling remains unresolved.
* A worker attempt to write beneath the host /root failed with EACCES.
  This single DAC check is not an escape-resistance assessment.

Package handling
----------------
Packages were downloaded as the ordinary host user into a dedicated
temporary directory. Worker installations were offline, with repositories
disabled and no external connectivity. --use-host-config supplied DNF
configuration, but not access to an enabled repository. Local RPM signature
checks were disabled for this compatibility experiment; it does not test
the eventual package-authentication policy. Package hashes are recorded.
DNF itself ran from the host tooling against an installroot; this does not
demonstrate DNF executing from a complete tool carapace. Only the resulting
shell and its commands were executed inside that root.

Interpretation
--------------
User namespaces plus idmapped mounts have demonstrated the desired numeric
ownership behavior, ordinary file capabilities, and same-policy SELinux
labeling on both tested filesystems. There is no demonstrated need for a
privileged helper for these successful operations.

Still to validate: different target SELinux policies; device-node needs;
restricted SELinux domains; capability and seccomp policies; complete tool
carapace builds; other kernels/filesystems; UID allocation; process cleanup
and escape resistance; networking/DNS; attestation interface isolation.

Follow-up: target policy independent of the build VM policy
=========================================================

Requirement
-----------
The target filesystem's SELinux labels must come from its own policy,
which need not define the same users, roles, or types as the build VM.
Same-policy success above is insufficient to establish this behavior.

Experiment
----------
Created an OFFLINE binary policy by decompiling a copy of the running
policy with checkpolicy -M -b -F, adding type conglobate_target_only_t,
and recompiling with checkpolicy -M -c 35. This provides a controlled
policy difference: the new type exists in the target policy but is absent
from the running policy. Verified both facts using setools. The target
policy was never loaded; the active VM policy was not modified.

Repeated experiments on disposable ext4 and XFS images with normal and
context=system_u:object_r:unlabeled_t:s0 mounts. Workers used the same
user-namespace and mount idmapping as the earlier experiment.

Results (both filesystems)
-------------------------
1. Direct worker setxattr(security.selinux) of the target-only label
   failed with EINVAL; a known label succeeded on a normal mount.
2. Worker setfiles -c TARGET_POLICY also failed with EINVAL. Supplying
   the target policy fixes userspace validation, but not kernel checks.
3. Running the worker's setfiles in setfiles_mac_t still failed with
   EINVAL. Permission in that SELinux domain does not give a child user
   namespace CAP_MAC_ADMIN in the initial user namespace.
4. Ordinary sudo root in unconfined_t also failed. The audit log records
   an explicit mac_admin denial for that domain. "Unconfined" is not a
   guarantee of permission for this operation.
5. Initial-user-namespace root running:

     runcon -t setfiles_mac_t setfiles -c TARGET_POLICY -F -v \
       -r ROOT FILE_CONTEXTS ROOT/parent

   succeeded on a normal mount. FILE_CONTEXTS assigned:

     /parent system_u:object_r:conglobate_target_only_t:s0

   Without -c TARGET_POLICY, setfiles rejected the label in userspace.
6. After the worker exited and the filesystem was fully unmounted and
   remounted normally, an authorized reader in setfiles_mac_t retrieved
   exactly system_u:object_r:conglobate_target_only_t:s0 on both ext4 and
   XFS. This establishes persistence, not merely setfiles' success status.
7. Readers without the necessary MAC administration permission, including
   ordinary sudo root in unconfined_t, saw system_u:object_r:unlabeled_t:s0
   instead. The stored target-only label was not lost: SELinux mediated
   its readback. The worker could read the file's content in this policy.
8. context= mounts rejected per-file SELinux label writes with EOPNOTSUPP
   for known and unknown labels, including the privileged setfiles path.
   They are not a solution for storing independent per-file labels.

The authorized readback used a disposable copy of getfattr labeled
setfiles_exec_t, run in setfiles_mac_t in the initial user namespace.
An initial attempt from /tmp was blocked by nosuid_transition; moving
the disposable executable into the experiment's private tmpfs permitted
the transition without changing host mounts or policy. This was a test
tool, not an implemented or hardened privileged service.

Kernel source explanation
-------------------------
security/selinux/hooks.c: selinux_inode_setxattr() attempts a forced
context conversion for an unknown label only if has_cap_mac_admin()
succeeds. That helper explicitly checks CAP_MAC_ADMIN against
init_user_ns and the SELinux capability permission. The getsecurity path
similarly distinguishes authorized raw-context readers.
Source inspected: https://github.com/torvalds/linux/blob/master/security/selinux/hooks.c

Implication
-----------
The tested direct user-namespace workflow does not meet the independent
policy requirement. A separate privileged labeling operation CAN store
and recover target-only labels without loading the target policy into
the VM, at least under the tested Fedora policy. Its privilege and process
boundary would require design and hardening before adoption.

Finalization-time setfiles is not a transparent substitute for arbitrary
chcon/setxattr calls during a build. Nor does it preserve arbitrary custom
labels automatically. Transparent writes AND reads inside the worker,
including inherited target-only labels, remain unresolved. No claim is
made that all possible target policies or labels have been tested.
